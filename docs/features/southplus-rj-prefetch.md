# South Plus RJ 元数据预取

目标版本：v1.3.0  
状态：已实现，并通过自动测试与本地浏览器夹具验证。

## 1. 背景

用户首次在 South Plus 打开 RJ 悬浮窗时，DLsite 域名可能尚未完成 DNS、TLS 和连接建立，同时作品元数据也未进入内存缓存，首开延迟明显。页面上通常已经存在可识别的 RJ code，因此可以在浏览器空闲且网络条件允许时，提前获取少量轻量元数据。

该功能在代码和 UI 中统一称为“预取（prefetch）”。不把 `<link rel="preconnect">` 作为主要实现，因为 Tampermonkey 的 `GM.xmlHttpRequest` 可能由扩展上下文发起，未必复用页面渲染进程建立的连接。实际的轻量元数据请求既能建立可用连接，也能产生可复用数据。

## 2. 目标

- 降低当前页面最可能被打开的前一至两个 RJ 弹窗的首次延迟。
- 复用正常查询层，不建立第二套网络和缓存逻辑。
- 不影响页面首屏渲染、论坛请求、计费网络或低速网络。
- 用户打开正在预取的 RJ 时，立即复用或提升已有请求。

## 3. 非目标

- 不预取页面全部 RJ code。
- 不预加载封面图片、音频或完整作品 HTML。
- 不提前搜索 South Plus。
- 不提前查询 ASMR ONE。
- 不保证每个页面都执行预取。
- 不通过增加并行连接数量换取延迟。

## 4. 候选识别

候选必须：

1. 通过统一的 `parseRjCode()` 校验并归一化。
2. 属于当前 DLsite 查询服务支持的编号范围。
3. 在当前页面去重。
4. 不存在有效成功缓存或正在执行的相同查询。

候选优先级：

1. 首屏或当前视口内出现的 RJ。
2. 距离视口顶部最近的 RJ。
3. 文档顺序靠前的 RJ。

实际网络请求最多选择两个。为避免已有持久缓存占掉网络名额，实现可按优先级检查最多六个候选的缓存状态；缓存命中和进行中请求不消耗网络预算。若只有一个未缓存候选，仅预取一个。

## 5. 触发时机

每次完整页面加载或刷新最多启动一轮初始预取：

1. 等待 `DOMContentLoaded` 和初次 RJ 扫描完成。
2. 等待页面进入空闲窗口：优先使用 `requestIdleCallback`，设置约 2 秒 timeout；不支持时使用 800–1200 ms 带抖动的延迟。
3. 调度前再次检查页面可见性、网络条件和用户交互状态。

MutationObserver 后续发现的新 RJ 默认不启动新一轮预取，避免无限滚动或动态页面持续产生后台请求。若未来需要支持，应另行设计每页总预算和长时间窗口，不属于 v1.3.0。

## 6. 网络准入条件

满足以下条件才允许预取：

- `document.visibilityState === 'visible'`。
- `navigator.onLine !== false`。
- 没有启用 `navigator.connection.saveData`。
- `effectiveType` 不是 `slow-2g` 或 `2g`。
- 当前没有用户触发的作品查询占用查询服务。
- 当前页面尚未消耗预取预算。

浏览器不提供 Network Information API 时，不因此禁止预取，但仍遵守可见性、空闲和预算规则。

## 7. 请求预算

v1.3.0 默认预算：

- 每次页面加载最多两个 RJ。
- 每个 RJ 最多一个轻量元数据 HTTP 请求。
- 默认并发数为 1，两个候选串行。
- 每个请求超时不超过 6 秒。
- 不自动重试。
- 总预取请求数最多 2。
- 预取失败不触发错误 UI，不持久缓存网络错误。

首选端点应是正常弹窗查询也会使用的 DLsite 轻量 JSON 元数据端点。端点选择由 `DlsiteService.prefetchWorkSummary()` 封装，调用者不得了解 URL。

## 8. 调度与优先级

建议流程：

```text
初次 DOM 扫描
  → 选出最多两个候选
  → 等待空闲与网络准入
  → 串行 prefetch(candidate[0])
  → 再次检查预算和用户活动
  → 串行 prefetch(candidate[1])
```

优先级规则：

- 用户点击或悬停同一个 RJ：复用 in-flight Promise，并将结果交给交互查询。
- 用户打开不同 RJ：暂停尚未开始的预取，先执行用户查询。
- 页面隐藏：取消尚未开始的预取；进行中的请求如果可以安全取消则取消。
- 页面恢复可见：v1.3.0 不重新补跑已取消的预取轮次。

## 9. 缓存语义

- 预取与正常查询使用完全相同的查询键和缓存。
- 成功响应写入正常内存缓存；是否持久化由作品元数据缓存策略决定。
- 用户打开弹窗时不得因为来源是预取而重新发起相同请求。
- 预取不能覆盖更新的强制刷新结果。
- 空结果是否缓存遵循正常查询规则，不建立预取专用负缓存。

## 10. 隐私与日志

- 请求只发送页面中已经公开出现并通过校验的 RJ code。
- 不向 South Plus 或 ASMR ONE 发送预取请求。
- 生产日志不记录页面正文、用户名、帖子内容或完整响应。
- 可选开发指标只记录候选数、是否命中缓存、耗时区间和取消原因。

## 11. 失败退化

任何以下情况都静默跳过，不影响原功能：

- 无候选 RJ。
- 网络条件不允许。
- 浏览器缺少空闲调度 API。
- 预取超时、取消或失败。
- GM 请求能力不可用。

用户正常打开弹窗时仍按交互查询流程加载，并显示正常的 loading/error 状态。

## 12. 验收标准

- 页面包含 0 个 RJ 时不产生预取请求。
- 页面包含 1 个 RJ 时最多产生 1 个请求。
- 页面包含 3 个以上 RJ 时最多产生 2 个请求。
- 两个预取默认不并发。
- Save-Data、2G、离线或隐藏页面不预取。
- MutationObserver 后续新增 RJ 不突破每页两个请求预算。
- 用户打开正在预取的 RJ 时不产生重复元数据请求。
- 用户查询优先于尚未开始的第二个预取。
- 预取不下载图片、不查询 ASMR ONE、不执行 South Plus 搜索。
- 预取失败不展示错误状态、不阻止弹窗正常查询。
- 单元测试使用虚拟时钟和假 HttpClient 验证调度与预算。

## 13. 实现与验证记录

- `PrefetchController` 已实现网络准入、缓存跳过、每页两请求预算、串行执行、用户查询忙碌检查与静默退化。
- South Plus 适配器只在初始扫描后调度一轮；后续 MutationObserver 不增加候选，并在页面隐藏时取消尚未开始的预取。
- DLsite Provider 复用正常 API2 查询键、in-flight Promise 和持久缓存；预取超时为 6 秒且不重试、不下载封面。
- 自动测试覆盖候选排序、去重、网络条件、串行预算、缓存候选跳过和交互忙碌退化；本地浏览器夹具覆盖初始两请求预算、动态 DOM 不追加预算以及用户交互优先。生产环境继续通过统一 QueryClient 的查询键和 in-flight Promise 保证连接复用语义。
